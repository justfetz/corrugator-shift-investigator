# Agent contract and teaching workbench

## Purpose and trigger

A user question wakes one bounded investigation. The agent requests evidence, optionally charts it, and returns a report. This is a learning/demo agent over synthetic records, with no scheduling or equipment authority.

## Current execution mode

The default OfflinePlanner is rule-based and understands only supported patterns. The Anthropic analyst plans once: its JSON plan is checked against the same tool allowlist and scope rules before any step runs, and a plan with one step outside them is refused whole (`plan_rejected`). Optional OpenAIPlanner implements native Responses function calling through the same dispatcher; see OPENAI_BYOK.md. AnthropicPlanner implements the same Planner contract over the Messages API with tool_use blocks and runs the hosted demo with a server-held key behind per-IP and daily round guards; see ANTHROPIC_DEMO.md. PeriodReports is a separate deterministic aggregation path. Live quality is scored by the golden set's live cases; the Anthropic recordings replay in CI, the OpenAI ones are not recorded.

The OpenAI adapter implements Planner.next_step(context), returning either a tool request or a final list of evidence IDs. The application validates both. The answer renderer retains deterministic calculated evidence. After successful daily investigation, the OpenAI adapter can write a bounded narrative with fact placeholders. Application code validates field references and substitutes their values. It labels prose as model interpretation; schema/reference checks do not prove its meaning.

## Context and memory

Application-owned production day, selected shift, a fixed process reference, available tool schemas and at most four recent question/scope entries accompany current-run evidence. Generated data and hidden scenario answers are not put into the prompt. Changing the day or dataset version clears incompatible history. Tool evidence IDs exist only for one investigation; a chart cannot reference another session/run's ID.

No conversation is persisted: the server keeps at most 32 in-memory contexts and three loaded day/scenario datasets, gone with the process, and no subscriber information at all.

**What the question log keeps (issue #125).** In the hosted demo the server writes one anonymous JSON line to stdout for each question the page asks, its answer, an analyst round on it and a thumbs up or down on its card ([the fields](DATA.md#the-question-log)): the question cut at 500 characters, with invisible characters removed and email addresses, IP addresses, personal numbers and key-like tokens replaced ([exactly what](DATA.md#the-question-log)); the rail's scope; the canonical address and measure it routed to, or the refusal; the status and the server time; the review flags; an analyst round's provider, status and call counts; the vote and an optional comment of at most 300 characters of plain text; the app version, the revision and the dataset hash; and two random ids, one per question and one per browser tab (sessionStorage), that only group a question's lines and a visitor's follow-ups. Cloud Logging keeps the lines for its default 30 days, and the BigQuery copy the owner reviews expires each day's partition after 90 days ([deployment](DEPLOYMENT.md#the-question-log)). A line never holds an IP address, a user agent, a cookie, a key or any other request header's value, the follow-up chain, the visitor's own rates (`rates=` is cut from a logged address), a model's prompt or narrative, or an evidence row; a test fuzzes the request headers to hold that. Cloud Run's own request log, like any web server's, records each request's URL (for `/q`, the question) with the visitor's IP address and user agent for 30 days; it is not copied to BigQuery, and the owner can exclude the `/q` entries ([deployment](DEPLOYMENT.md#the-question-log)). The loopback workbench writes none unless `QUESTION_LOG=1`, and `QUESTION_LOG=0` turns the hosted demo's off.

The local server retains at most 32 in-memory contexts and three loaded day/scenario datasets. Browser controls own date/shift selection; the follow-up parser preserves the selected day. Ambiguous date-range questions fail explicitly in offline mode.

## Tools and permissions

- get_shift_kpis: output, gross area, downtime by kind (and maintenance plus operator as `op_maint_pct`), waste (dry-end over the yield after trim and shear, `yield_sqft`), throughput and lineal per setup/run; each banded figure carries the owner's band (`<measure>_band`, `<measure>_band_text`; issue #101).
- get_downtime_breakdown: allowed kind filter and grouping by reason, place or kind, with stops and minutes per stop; external downtime (a power outage, kind `External`, `external`) and then planned maintenance (`scheduled`) sort last, after the unplanned maintenance and operator reasons. The model's kind filter is Maintenance, Operator or Scheduled (v1's `PM` still answers as Scheduled); external stops are read unfiltered. On a record-store day, `flags`: the shift's maintenance or operator downtime over its band, with the supervisor slot and the leading reason's recurrence.
- get_wet_end_performance: actual elapsed-time speed versus grade-specific target, and running speed (stops out) versus the grade's trailing-year baseline (`baseline_fpm`, `baseline_gap_ft`, `under_baseline`; `runs_under_baseline` on the envelope).
- get_quality_breakdown: rejected area by the expanded warp, bond and misalignment observation categories.
- get_shift_overview: KPI row plus largest losses and three chart evidence components from fixed queries.
- get_order_matrix: dimensions, outs, cuts, requested/planned/produced sheets and remaining quantities per fragment (the record families carry no order ledger, so requested and remaining sheets are null).
- render_chart: supported bar or line specification referencing a successful result from this run.

Period tools read the whole record store (the rolling year, Monday to Friday) instead of the selected day. Each takes a `window` of `{"period": "day|week|month|fiscal", "anchor": "YYYY-MM-DD"}` (fiscal = the 4-4-5 accounting period; KPI envelopes flag unequal production-day counts) — week is the Mon–Fri production week containing the anchor, month the calendar month, and the previous window is computed the same way — plus an optional `shift` (null = all three shifts; under Selected shift only the selected shift is enforced in application code). All are read-only, bounded (fixed queries, bound values, 1,000-row limit, two-second interrupt), and return `window`, `previous_window`, `coverage`, `source_rows` and rows whose percentages are ratios of sums (METRICS.md).

- get_period_kpis(window, compare, shift): the dashboard tiles with current, previous, delta, `better` direction and a `change` label; deltas withheld unless both windows are complete. The envelope also counts `order_changes`, the setup records an order change started (change code O), with `previous_order_changes` and `order_changes_delta` (null, never zero, for a window with no shift records; the delta only when both windows are complete; issue #113).
- compare_periods(current_window, previous_window, shift): the same table for two arbitrary windows.
- get_downtime_pareto(window, group_by reason|place|kind, measure minutes|count, shift): ordered with share and cumulative share, previous-window minutes alongside.
- get_waste_breakdown(window, shift): every waste line (trim; shear and the changeover rejects counted with it; the cutoff-knife and stacker waste boards; the dry-end families bond, warp, misalignment, moisture and other, and their total; planning / admin apart; bale and unexplained), plus `details` (reported dry-end reasons with share of dry-end), as sq ft and % of gross, with the previous window; the dry-end families and their total also as % of the yield after trim and shear (`pct_of_yield`, issue #101), and trim, shear and dry-end with the owner's band (`band`, `band_text`); `good_output_sqft` and `good_output_pct` (gross minus every recorded waste line, owner 2026-11-12) and `yield_sqft`.
- get_stops_profile(window, shift): stops, minutes and minutes per stop per production day plus the Mon–Fri weekday profile.
- get_trend(metric, weeks 1–26, anchor, shift): weekly series of one allow-listed metric.
- get_grade_totals(window, shift, measure volume|speed): per board grade, setups, wet ends, lineal ft, volume MSF and share, speed without stops and elapsed speed from the setup clocks, % of grade target, allocated stops and minutes, lineal per setup and per paper change, trim and dry-end %, previous window's volume. `measure` chooses only the lead and the chart, never the rows: volume (MSF beside the previous window, the default) or speed (ft/min without stops against each grade target).
- get_overrun(window, shift): nominal versus actual cuts per knife (cuts, sheets, % of nominal) with the share of customer lines inside, over and under the ±2 % band; last row all knives.
- get_rollstock(window, shift): paper consumed from the wet-end (paper run) records: lineal feet and MSF per board grade and web width, paper runs and feet per run, previous window's feet, MSF and runs with deltas. MSF is the paper footprint (feet × width / 12 / 1,000); the records carry no basis weight, so no tons. All shifts count whole runs on the production day they started; one shift counts the setups it ran on each run, so a run spanning two shifts is in both.
- get_shift_dollars(shift): each downtime reason, the speed gap to 675 ft/min, side trim, shear, the changeover rejects, the cutoff-knife and stacker waste boards (each its own gap, priced once: owner ruling (d), issue #100) and each dry-end reason priced at the assumed rates (paper, machine time, per year; contribution null with 'margin not set' until a margin is set), the recorded losses ranked by dollars; planned maintenance and a power outage carry `apart` (schedule-driven, external), no rank and no part of the recorded-losses total, and `all_in_usd` adds them; side trim stays ranked and in that total, with `control` `schedule-driven` from `targets.json`'s trim band lever (issue #135; docs/COST_MODEL.md).
- get_day_dollars(shifts): the same gaps summed over the listed shifts that are complete (all three when omitted) and priced once on the day (an incomplete shift is named in excluded_shifts, not added); the offline planner adds it, with the answer's shifts, to a dollars answer over more than one shift for the card's total. Not in a model's catalog and not on the analyst's plan allowlist, and the scope check refuses it for a shift outside the selected scope (issue #31b review).
- get_opportunities(window, shift, lens): the levers ranked in $/yr (the speed of each run under its grade's trailing-year speed, trim over target, each downtime reason, shear, the changeover rejects, each dry-end family: bond, warp, misalignment, moisture, other), each with the records behind it and marked `controllable`, `schedule-driven` or `external` (a power outage), and under the ownership lens `unattributed` (the unexplained remainder) or `not production waste` (planning / admin); ranks levers, prescribes no adjustment. `lens`: `all` (default), `supervisor` (the controllable losses ranked, schedule-driven then external after), `ownership` (the total cost of waste, side trim first, then every other line of the waste breakdown priced once: shear, the changeover rejects, the cutoff-knife and stacker boards, planning / admin and the unexplained remainder, the dry-end kinds as one tag-scrap subtotal with each kind beneath it; its total is the waste breakdown's). Each reject family's `control_note` is its own cause from `reject_reasons.json`.
- get_downtime_review(window, shift): the owner's downtime answer (issue #101): maintenance and operator downtime against their bands as % of scheduled minutes; every reason by kind ranked by % of scheduled minutes with stops and minutes per stop, external downtime (a power outage, kind `External`) apart and planned maintenance last as scheduled time, neither in a band; `flags`: each shift over a band with its supervisor slot and the leading reason's recurrence over the trailing year. Offered to the Anthropic loop and the analyst's plan; the OpenAI loop leaves it out for its byte cap.
  Neither money tool is offered to a live planner yet (the Anthropic tool loop and plan catalog, the OpenAI loop); the offline router plans them.
- get_speed_opportunity(window, slice_by width|crew, shift): per grade and width (or crew), typical speed without stops vs the best fifth of setups, % of target for both, gap, opportunity hours, dry-end % of the fast fifth vs the rest; short setups excluded and counted; no temperatures modelled.
- get_speed_variance(window, shift, against baseline|previous|shift, against_shift): the gap between a reference speed and the window's speed with stops in ft/min and lineal ft, every grade held at its trailing-year baseline (issue #101), split into stops (unplanned), planned maintenance and external stops (each its own bucket when either side has one), setups (order changes), running under the grade's baseline and grade mix, which add up to it; `details` splits each bucket by stop reason or grade; each bucket is marked controllable, schedule-driven (the grade mix, planned maintenance) or external, and each controllable loss bucket is priced as machine time, the others never (docs/METRICS.md, Speed variance). `against_shift` is another shift, so the selected-shift scope refuses it. Offered to the Anthropic loop and the analyst's plan; the OpenAI loop leaves it out for its byte cap.

- semantic_query(measure, window, group_by, filters, shift, compare, order, limit, share): one request of the semantic model (issue #117; phase 2, issue #144, has the offline router plan it for a question the semantic model's parser reads completely; [the model](../src/investigator/semantic_model.json)): a measure of `semantic_model.json`, up to two of its dimensions, one value per filtered dimension, the window, one shift or all. `semantic.validate` refuses an unknown measure, dimension or value with the nearest valid choices (or, with nothing near, every value the records hold), a dimension the measure's records do not carry (setup feet by order would count a setup once per lane), a time dimension as a filter, and a filter outside the measure's own records (operator and maintenance downtime of the External kind would read as a recorded zero: the refusal names the measure's kinds and the measure that counts every kind); `semantic.compile_query` writes the SQL from the model file's tables, columns and expressions only, every request value bound and every statement with a LIMIT (an entity's `where` is read by a small grammar when the model loads, an error DuckDB still raises is a refusal, never a server error, and a result whose listed rows of an additive quantity do not add up to its total is refused, never shown); it runs under the two-second interrupt, and its receipt is the trace plus each row's `source_ids` (the first fifty ids of the records it sums, sorted: stops, setups, shifts, and reject and lane lines by their own identity) and `source_count`. `compare=previous` is refused beside a time split, whose rows have none in common with the window before. `share` (the review of PR #155) names one value of the single, non-time `group_by` dimension of a count or a sum: a statement of its own reads that value's row from the whole split (its share DuckDB's, a value with no records a zero row), appended when the limit left it out, and the result says which row it is (`share_row`); it is refused beside a compare, a second split, a ratio or a filter on the same dimension, and absent from the arguments when unset. A fewest-first (`order=value_asc`) split by one dimension of a sum or a count lists every value the store holds (a time dimension's: the window's scheduled days or buckets) the records do not, as zero rows DuckDB adds, so a fewest is never a value with records while another has none; not for a ratio, a filtered dimension or one the measure's own filter keeps to. Every result and row carries its lever: the slice's or filter's own (planned maintenance schedule-driven; a power outage and the External kind external, from `targets.json`'s external block), else the lever of the band the value is read against (each stop kind's own), else the measure's. A measure with a band (its own, its dimension's, or the line it counts setups over) reads its lever from that band in `targets.json` and types no copy, and the model refuses to load when a measure over the same quantity names another: the band's quantity in any unit, the dollars priced from it and the ratios over it (trim feet and trim dollars beside the trim band), and every measure over an entity whose rows are a band's quantity (the reject lines, in square feet or sheets, beside the dry-end band). A filter that keeps other records is another quantity: maintenance plus planned-maintenance minutes are schedule-driven, not the maintenance band's. Reached by its address (`measure=semantic`, [URLS](URLS.md)) and the value goldens; not in `TOOL_SCHEMAS`, and `Agent._execute` runs it only for a request whose plan names it (its address) or a scripted planner that is no model, so a model that writes its name is refused like any unknown tool until phase 2 wires the router and the analyst to the model. It reads the store's tables as they are: the store never holds the data-quality demo's excluded record, and every setup of the record year passes the checks `shift_kpis` applies, so its sums are the period tools'; reading through those checks is phase 2's when a record can fail them. A priced semantic answer is priced at the rates of its address (`rates=`); the card's rates panel does not re-price it in the browser yet. Its answer has its own shape (below).

Forbidden: shell, arbitrary SQL/code, external URLs, filesystem browsing, machinery control, schedule changes, subscriber access or email sending. SQL values are bound separately and grouping identifiers are allowlisted.

## What each tool read

Every step of an answer declares the store table it read and the filter it read it with (issue #142, `datapages.SOURCES`), so a receipt "(query N · row M)" links to the rows behind its figure in [the data browser](URLS.md#the-data-browser). The server attaches the declaration to each trace entry as `source` (`table`, `filter`, `url`, `rows`: one `/data` address per row of each cited list, and `also`: the other rows the step read, a comparison's previous window over the same table, the trailing year of setups a grade baseline comes from, and the notes' shift record); it changes no tool, no row and no answer text, and a model never sees it. The filter is the step's window (`from`, `to`, or `day` for a one-day window) or the selected production day, plus its shift when it read one; a cited row narrows it further:

Each section of an answer has its own receipt (`receipts`, [the grammar](URLS.md#the-data-browser)): a finding about the previous window opens that window's rows (a bullet under the label "The previous window" only when it cites the whole result of the step the label's group cites), a flag's recurrence count the reason's stops over the trailing year it counts, a shift summary finding the table its figure is read from, and a quantity answer's figure (#113) that its step's rows do not hold the rows that do: a stop kind's minutes or stops that kind's stops (`kind=Maintenance`), the window's order changes the setups an order change started (`change_code=O`).

`tests/test_datapages.py` holds it on the golden set (the answers of its addresses, and of its cases asked without one: by POST, in turns, or as an analyst's scripted plan) and the data-quality demo's day: for every section that cites a step, it recomputes the section's **bold figure** from the rows its receipt opens, with the receipt's own filter, and compares it with the figure as printed: sums, counts, ratios of sums, the tiles from the `shift_kpis` rows, previous windows, recurrence counts, both numbers of an "N of M" count, the speed gaps and their buckets at each grade's baseline (from the trailing year's setups), and every dollar figure as its quantity from the rows priced by the cost model at the answer's rates (the visitor's `rates=` included). A total is recomputed from its own receipt, never from its parts' links: a money total as each lever's own filter over the total's day, span and shifts, priced over the receipt's rows; a speed gap as both sides split from the receipt's rows, any row on neither side a failure. A money total reads the step's `shift_kpis` rows, each shift once, and a speed gap's rows must sit on one side or the other, each record once, with the sign the section states. The checker also mutates the receipts and fails if a figure survives one that opens other rows: each money total a production day earlier and each speed gap a week earlier (the reviewer's M5 and M7 on #151), each shift row beside its data-quality variant, and against the previous window a bucket's rows of this window alone. A semantic answer's figure is its measure's expression from the model file over the receipt's records (a ratio's denominator over its declared rows). A section without such a check fails. The browser runs no tool and no model: it reads the store's tables under the same lock and bounds as the tools.

## Bounds, failures and done

Default offline bounds: 20 tool calls and a ten-second loop deadline checked between planner steps. The server configures live mode for ten tool calls and 60 seconds; the adapter also caps model calls at ten and uses bounded socket timeouts. Agent context is limited to 200,000 serialized characters; the live serialized request limit is 24 KB for the OpenAI adapter and 64 KB for the Anthropic adapter, which trims the oldest tool results to a stub before refusing a request. DuckDB queries use a two-second interrupt timer and a 1,000-row limit, and every connection runs with DuckDB's join filter pushdown off (`analysis.DUCKDB_CONFIG`: in DuckDB 1.5.1 it lost a LEFT JOIN's matches under CPU contention, found on the review of PR #148). Failed tool validation consumes a call. Period aggregation bypasses the agent loop and is bounded by the fixed demo calendar rather than these loop deadlines.

These are local-demo controls. The synchronous planner deadline does not preempt a blocked third-party adapter; any future adapter must enforce its own HTTP timeout, token/output limits and an application-wide spending reservation before making calls. Offline mode makes no model calls. Explicit OpenAI mode reserves spending before each request; no real API calls have been made during automated validation.

Intended done condition: supported analysis has successful referenced evidence and any requested charts. Finish validates successful evidence IDs. Explicit chart/graph/plot requests without a chart return partial, and overview evidence automatically supplies its three charts. Semantic fulfillment is not guaranteed. See review R4. Incomplete data must be disclosed and must not be ranked as valid performance. A daily run can be complete while its evidence coverage is incomplete. Period status is partial when its window has missing/invalid contributions. A recorded symptom does not establish a mechanical cause.

## Answer shapes

An offline answer's `sections` are a shape per intent (issue #75, `shapes.py`), built from the tool rows the answer already has; no new number is computed, only rows chosen (the largest reason, the slowest run, the three slowest grades) and counted. They stay plain text with two markers, so the Markdown export, the PDF and `/evals` read them unchanged:

- **Headline**: the first section with a `**figure**` that is not a bullet. The figure is the asked measure with its unit (speed against grade target for "why was this shift slow", the slowest grade for "what grades ran slowest", minutes at the top reason for a Pareto); the rest of the line is what it is held against: a target, the previous window, the other shifts.
- **Findings**: `- ` bullets right under it, three to five for a diagnosis, each with exactly one `**figure**` and its evidence `(query N · row M)`: step N of the trace, as the query box numbers it, and the row of that result the figure is a value of (`detail M`, `weekday M` and `flag M` name a result's sub-reason, weekday and flag lists; no row, a count of the result's rows or a total its envelope carries). A list of like items longer than three is bullets or a table, never one sentence; the client shows five findings per card and folds the rest under one "more".
- **Labels**: a short line without digits or final punctuation introduces the bullets after it (`Reported sub-reasons`, `Most downtime`, `Weekday profile`) and renders in small caps.
- **Where to look**: two or three bullets after the label `Where to look`, each naming a place in the records, never an action, and ending with the question that opens it, `→ “Show the setup matrix”`. Each is a question the offline router answers in the same scope; the client links it to that question's address.
- Anything else is a plain sentence of at most about forty words: the window and its coverage, a tool's note split into its sentences, a caveat, a reported note. After the findings the client sets these under the charts, so the chart follows the findings directly; a data-quality warning stays with the findings.
- Every number on a line that cites a row is a value of that row (or a count of the result's rows, or a rule constant): a line never states a figure from a row it does not cite, and a rank ("the lowest of the three shifts", "the highest of 16 runs") is said of the figure the row was chosen by. The chart for the answer's measure comes first: a speed-led answer (why slow, compare) shows speed against grade target, then the downtime that explains it.

One quantity (issue #113) takes it too. A count or unit question ("how many setups last week", "how many minutes of maintenance downtime yesterday", "what was our lineal per setup") is planned as `measure=quantity&metric=…` and opens with that quantity in the unit asked (`**N setups**`, `**N minutes** of maintenance downtime`, `**N ft per setup**`, `**N sq ft** of Side trim`), then the previous window and the band; the findings are the tiles it is made of (setups: paper changes, feet per setup, lineal feet; stops: downtime minutes, minutes per stop, downtime %), and the other KPI tiles fold under a label. The tool is the one that carries the quantity: the KPI tiles (order changes from their envelope), the downtime review for maintenance or operator minutes and stops (each reason of that kind after it), the Pareto for one stop reason or place (`reason=`, `place=`: its stops or minutes, the largest other reasons after it), the over/under-run for sheets (each knife after the total), the totals by grade for the setups, paper changes or lineal feet of one named grade (`grade=`; stops and downtime by grade are refused: they are recorded by shift, reason and place). A countable noun with no count asked ("how did we do on setups this month", "compare stops this week to last") is read as that count rather than answered with the KPI summary, and a count over each shift, or of setups at a stop place, is refused: a quantity is one shift or all shifts together, and setups are the line's. An area or a percent of one waste line ("how many square feet of trim", "what percent was shear") is that line of the waste breakdown (`metric=waste_sqft` or `waste_pct`, `waste=`; a dry-end line as a percent of the yield after trim and shear), and waste in MSF is the bale (`metric=bale_msf`). A duration ("how long", "how much time", "minutes of") is minutes: of downtime, of a kind, of a stop reason or place, and a changeover's time is its order change stops; how long a setup or run took, how long the line ran slow (slow is a speed: "how long were we slow"), downtime in hours, any ratio the records do not keep ("minutes per setup", "sheets per order", "feet per stop", "setups per day", "sheets per minute", "square feet per minute", and any numerator the records do not keep per anything: "cost per setup", "yield per setup") and reject sheets are refused with where they are answered. The ratios kept are feet per setup, feet per paper change, minutes per stop and MSF per production day (`metric=msf_per_day`, "what was our MSF per day this week", "how much did we make per day"), and the downtime of each production day is the stops profile's (`metric=downtime_per_day`, "downtime per day this week": the day with the most minutes first, then each weekday's minutes per day). An average or typical stop is minutes per stop ("average stop length", "how long is our average stop"); an average of a total ("average stops this week"), across a window's days ("average downtime per day"), of a setup or run, or of a stop reason, place or kind (each reason's minutes per stop are in the downtime review, and the refusal says so), and the longest or shortest of anything (no tool returns a maximum) are refused, as are a percent per day, a share of the waste ("what percentage of waste was dry end") and dry-end rejects asked as a percent of gross. "Per" is a ratio only before a count or a span ("per setup", "per day", "per minute"): "downtime per reason" and "rollstock per width" are groupings, and a speed per day or in lineal feet per minute is the speed answer. Stops or minutes of each place, reason or kind ("how many minutes of downtime at each place", "for each stop reason", "stops by kind", "downtime breakdown in minutes") are the Pareto grouped by it, in the unit asked, and per day they are refused; any other quantity grouped ("minutes per stop by reason", "setups at each place") is refused; a breakdown asked in a unit ("waste breakdown in percent", "waste lines in percent") is the breakdown; a comparison of shifts ("compare shifts on downtime minutes") and a quantity of a ranked shift ("the slowest shift", "the best shift") are refused, the latter because the router cannot rank shifts while it reads a question. A question that asks for a number and names no shift answers every shift together, whatever the shift control says, with or without an ask word ("how much downtime this week" as "total downtime this week", "feet per minute this week" as "how many feet per minute this week"): one quantity, each production day's stops or downtime, the downtime review, the Pareto, the waste breakdown, volume or speed by grade, a window's speed, rollstock and the over/under-run, when their all-shift answer is the same tools with only the shift moved (the owner's scope ruling of 2026-11-13; `question_scope`, `agent.NUMBER_INTENTS`, `read.all_shifts`). With no window named it is the selected day, the downtime review's too (the ruling retired #101's previous production day). "This shift" or a named shift keeps the shift, and so do the investigations (why, what caused or drove, where it came from, what went wrong: `agent.WHY_ASK`, which never land on a quantity route), dollars, trends, the KPI summary and a production day's per-shift answers (its speed, quality and downtime by place or kind, whose all-shift form is the three shifts compared). The overview, the summary and the shift comparison, which opens with speed, answer "why was it slow", "summarize" and "which shift ran faster": a quantity asked never lands there either. One quantity, minutes per stop, each production day's downtime and the stops of each production day are answered only when every word of the question is consumed (`agent.allow_list`, round 6 of the review of PR 143): the ask words, the measure's noun and unit, the filter the route applied with the connector before it, the window, a window compared with the one before, the shift, a kept ratio's "per" and the average it is, and the closed table `agent.FUNCTION_WORDS`. Any other word ("brief stops", "stops at the slitter", "planned downtime", "stop rate", "90th percentile"), and a rolling window ("the last 7 days"), is refused with what it asks for and at most three questions that answer; stops said beat any other count noun ("how many stops were order changes" are the stops with that reason). And a ratio kept for all stops or for the line asked of one stop reason, place or kind is refused, as is the stops profile (`get_stops_profile`, every stop of each production day) asked of one or as an average across the days; "a day" and "daily" read as "per day", and "each day", "every day" and "by day" too when the question is about stops or downtime (`agent.per_day`), an average stop is its length only ("average stop cost" is refused), "how long … per stop" is minutes per stop and "feet a minute" the speed. The KPI summary (`measure=kpis`) is for "how did we do": the router never answers a question that names a countable noun or a unit with it (`agent.catch_all_guard`), and a count of something the records do not hold (rolls, boards, step-ups, every splice, distinct orders, hours, weights), or a stop reason, place or dollars named with no count or unit ("how did we do on glue"), is refused with what can be asked.

Money (issue #31) takes the same shape. Where the money went this shift is a headline total with its per-year figure, then each gap ranked by dollars as the tool ranked it. Where the money is over a window is the levers' total a year, then each lever with the records behind it. A priced row elsewhere (a downtime reason, a reject reason, a Pareto row, a waste row, a speed-opportunity cell) carries its dollars and per-year figure beside its quantity on the same bullet. The rates line, the cost note, the contribution status and one row's pricing formula, quoted as the cost model wrote it, read as caveats under the charts.

The offline router's semantic step (issue #144): `semantic_parse.read` reads a question into a `SemanticQuery` with the model's own words (measure, dimension and value names and synonyms; the store's values), the router's window and shift words, and one closed table of ranking, grouping and statistic words; it makes no model call and runs in milliseconds. Every content word is used, or the reading is refused with at most three questions, each one the parser reads completely. `agent.parse_request` asks it after the hand router: a complete reading is planned as one `semantic_query` step (its address `measure=semantic&m=…`, with `rank=`, `top=` and `share=` when the question ranked or asked a share, `share=each` for every row's share, `vs=` for two values compared, which the card names first; a percent of the shift or of the scheduled time is a percent of the scheduled minutes, never a share) when the hand router refused the question or answers something else; a reading that asks a ranking, a share, a statistic or a ratio the KPI summary or a catch-all route drops is refused, and so is a median or an average the model does not define, a share it cannot place or a shift named beside a split by shift over the review, the Pareto or a summary, and a superlative with no measure ("worst shift") over the overview or the summary; a question the hand router refuses with its general help ("Offline mode supports …") shows the reading's own refusal when it asked a ranking, a share or a statistic ("best crew"); the investigations (WHY_ASK) are never read, and the flagship shapes (the review, the Pareto, the waste breakdown, the money, the setup matrix, the speed variance) keep every question they answer. No model planner is offered `semantic_query` yet (#104 has the live model fill in the same `SemanticQuery`).

A semantic query (issue #117) has one generic shape: the asked measure first, its label, filters, shift and window words, then the value over the whole window as the bold figure (`Downtime, stop kind Maintenance this week: **87.85 min** (query 1)`), with the previous window and the owner's band beside it when the query has them (a change only when both windows are complete; a previous window outside the records said so); then one finding per row of the split in the query's order, each citing its row (`- 26-C: **11.15 min** · 12.69% of the total (query 1 · row 5)`), five before the label `The rest, in the same order`, a slice banded only when it is a ratio of its own (a reject family read against all the yield carries no band; a grade does; a grade's maintenance minutes against all the scheduled minutes do not, a shift's against its own do) or its dimension names the band (each stop kind its own), and a filter cuts as a split does: a figure whose filter or row cuts the numerator and never the denominator (downtime % of one grade, dry-end % of one customer) carries no band, is read `of all the window's scheduled minutes` or yield (or `all the shift's scheduled minutes in the window`, the grade's, the week's: the slice the denominator does carry, which the window may cut short), and one line says it is the slice's part of the whole, and, for a slice with a clock or a yield of its own (a grade, a customer, an order lane), not its own rate, a slice whose lever is not the measure's saying so, a percent's change in points; an incomplete window said so and its rows never called a ranking; the window, the measure's definition from the model file and, for a priced measure, how a dollar is priced; and where to look in the flagship answers for its kind of record.

An incomplete window (coverage other than complete) is listed, never ranked: no "Slowest", "the largest" or "the most of", its rows in the tool's order, and one line saying rankings are withheld; a daily shift with excluded records was already reported and never ranked. A tool called twice for a shift (downtime by reason, then by place) keeps a finding for each call.

A shape depends on the plan that ran, the one quantity a count question asked for (its address carries it as `metric=`), and the scope, never on the wording of the question, so a question and its canonical address answer with the same sections ([URLS](URLS.md)); the period intents the URL grammar resolves as aliases (a day-shaped downtime or quality question under a ranged window, and dollars over a window) share the Pareto's, the waste breakdown's and the levers' shape. An analyst's own plan is shaped by the tools it ran, and every other result keeps its own finding, so the calculated evidence under a narrative never drops a result it can cite. The evals hold the shape from outside: every bold figure must be a value of the row it cites (`evals/README.md`, global invariants).

## Interface and transport

One screen offers date/shift scope, questions, calculated metrics, charts, report download and expandable tool/context/SQL traces. It labels synthetic data and offline planning. No fabricated email signup/success flow exists.

By default the server binds only to 127.0.0.1. It enforces Host, Origin, a random request token, JSON content type, 16 KB request bodies and a shared 60-requests/minute limit. Static files have an explicit allowlist and a restrictive content security policy. Labels are rendered as text, not HTML. The hosted demo runs the same single process in public mode (below, and [deployment](DEPLOYMENT.md)); it is a demo, not a multi-tenant service.

Optional WebMCP registration invokes the same visible investigation action and validates its question argument. Browsers without support use the ordinary interface. Browser-level WebMCP execution has not been verified; no claim of that validation is made.

New read tools: get_setup_matrix(shift), get_shift_notes(shift), get_rankings(shift, metric). Metric is restricted to speed/downtime/quality. Notes are bounded to 1,000 characters, passed as untrusted evidence, and rendered with text nodes or escaped PDF paragraphs. They cannot expand tools or shift scope. Selected-shift mode is enforced in application code even for a malicious model call. Daily OpenAI matrix results show the model at most 12 preview rows with explicit disclosure; the UI retains the full validated matrix.

The Period control is part of the scope. Under Week, Month or 4-4-5 the agent passes the selected window to the planner (`Context.period`; the offline planner uses it as the default window and turns day-shaped questions into their period form) and refuses any daily tool with the window to use instead; a window the question names still wins. The offline router gives measure words precedence (issue #74): a speed or volume word decides the intent and a grouping word only chooses the breakdown, so "fpm by grade" is speed against each grade target, never volume. ## Reference: how the router breaks ties

The offline router gives measure words precedence (issue #74): a speed word (speed, fpm, ft/min, fast, pace, slow/slower; "running" only beside one of them) or a volume word (throughput, output, volume, made, produced, MSF, lineal, footage) decides the intent, and a grouping word (by grade, by width, by crew) only chooses the breakdown, so "fpm by grade" is speed against each grade target (`measure=fpm&by=grade`), never volume. Both parse paths, the day path (`_parse_request`) and the period path (`parse_period_request`), take that decision from one function, `agent.speed_or_volume`, so a phrasing cannot route one way with no window and another way with "this week": the two paths diverging is where the next routing bug comes from, so a new speed or volume word goes in that function and nowhere else. A volume cue attached to a volume ask ("how much did we make", "ran the most", "share of output") beside a speed word keeps the question volume; a loose "most", "share" or "how much" does not ("which shift lost the most speed" is speed), but a bare volume word does not veto a speed word ("did we make our speed target this week" and "speed and output" are speed), a loss word (stops, downtime, waste, trim, rejects, quality) keeps a "slow" question on the losses, and a speed word that asks how fast a paper change, changeover or setup went ("how fast did we change paper", "how quick were the changeovers") is a setup question, the setup matrix (`measure=setups`), never line speed, while a line-speed question that only mentions one stays speed ("fpm by grade after changeovers", "how fast are we running between changeovers") and a diagnosis stays the overview ("why was this shift slow on changeovers"). Like every setup-matrix question it is refused under the Week, Month or 4-4-5 control, and with a window named in the question ("… this week") it is refused with where it is answered (the setup matrix on Day, or the order change stops over the window): the window's KPI tiles answered it with MSF first until issue #113. A speed question over a named window ("average speed this week", "our speed vs last week", "how fast did we run in August") runs the period speed plan, a volume question over one ("throughput this week") volume by grade; a diagnosis cue (why … slow, slow, bad, killed) stays on the overview form at every grain ("why was this shift slow this week" is `measure=overview&window=week`), never a speed plan alone, and a grade word does not override it ("why was 275-BC slow this week"); the one exception is "slower than normal", which reads the weekly speed trend until the baselines of #76 exist (its golden, `speed-slower-than-normal`, carries a note saying so); two named months stay on `compare_periods`.
